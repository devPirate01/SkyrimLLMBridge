Proposed response to supervisor feedback
1. Revise the research questions

The questions should concern system properties that can be measured without participants.

Proposed primary research question

To what extent can a locally hosted and domain-adapted language model generate structured, contextually appropriate NPC dialogue while conforming to the deterministic constraints of a bounded Skyrim quest on consumer-grade hardware?

Proposed subquestions

How accurately do the evaluated configurations select valid policies, response types, clues, identifiers, and actions under the defined quest states?

How reliably do the evaluated configurations resist forbidden-state leakage, unsupported knowledge claims, malformed output, and prompt-injection attempts?

How consistently do the generated responses preserve the NPC persona, epistemic boundaries, and diegetic setting across repeated runs?

What latency, throughput, memory usage, and failure rates occur when the selected models operate locally on the target consumer hardware?

These questions avoid user experience, engagement, immersion, and preference.

2. Separate development and held-out cases

The current 35-case collection should not automatically become the final test set because it has already influenced prompt development, fine-tuning, validator rules, and model selection.

Use two distinct groups:

Development set

Used for:

prompt construction;
policy design;
dataset debugging;
fine-tuning decisions;
validator development;
inference-setting selection;
reasoning-mode decisions;
fixing implementation errors.

The existing 30-case and 35-case benchmarks should normally be classified as development cases.

Held-out final test set

Create a new set that is frozen before the final runs. The held-out cases should:

express similar policy categories using unseen wording;
include unseen combinations of quest state and conversational intent;
include paraphrases not used in training;
include adversarial inputs not used during prompt development;
include repeated-turn scenarios;
include boundary cases around clue disclosure;
remain unchanged after final experiments begin.

The held-out answers must not be generated from the model outputs. Expected outcomes should be specified independently before running the models.

6. Use AI judges only for genuinely qualitative properties

The AI judge should not assess:

JSON validity;
policy correctness;
clue legality;
identifier validity;
action permission;
quest-stage correctness;
latency;
throughput.

Those are deterministic.

AI judges may assess:

persona adherence;
diegetic consistency;
Skyrim-appropriate tone;
epistemic consistency where exact matching is not possible;
conversational coherence;
naturalness and fluency;
relevance to the player’s message;
unnecessary repetition.

“Naturalness” must be described as judge-assessed textual naturalness, not player-perceived naturalness.

7. Strengthen the judge protocol

Before final testing, freeze:

exact judge model names and versions;
provider or local checkpoint;
judge system prompt;
scoring instructions;
contextual information shown to the judge;
temperature and decoding settings;
number of repeated judgements;
handling of failed or malformed judge responses;
aggregation procedure;
disagreement procedure.
Recommended controls
Remove the candidate model’s identity.
Use neutral labels such as Response A.
Do not tell the judge whether the response is base or fine-tuned.
Use at least two judge families.
Repeat scoring, preferably three times per judge if affordable.
Randomise item order.
If comparing responses pairwise, reverse response order.
Keep output length visible but instruct judges not to reward verbosity.
Use structured JSON judge outputs.
Store all raw judge responses.
Agreement reporting

Depending on the design, report:

weighted Cohen’s kappa for two judges;
Fleiss’ kappa for more than two;
intraclass correlation for numerical scores;
percentage agreement;
rank correlation if systems are being ranked.

Agreement should be reported per dimension, because judges may agree on fluency while disagreeing on persona.

8. Manually audit the judges

Frank’s manual-audit requirement can be addressed without creating a participant study.

The researcher can manually inspect a predefined sample, for example:

a random proportion of all judged outputs;
all extreme scores;
all judge disagreements;
all outputs containing suspicious instructions;
all outputs that pass the judge but fail deterministic rules.

The manual audit should determine whether:

the judge followed the rubric;
the score explanation matches the score;
the judge ignored injected instructions inside the candidate output;
verbose outputs received unjustified advantages;
repeated template responses received inflated naturalness scores;
lore-like language hid factual or policy errors.

This is quality assurance of an automated evaluation pipeline, not a player study.

10. Choose meaningful baselines and ablations

A useful final comparison should answer what each architectural decision contributes.

Strong baseline candidates

Same:

Difference:

This isolates the effect of fine-tuning.

Baseline B: Larger untuned model

The 26B-A4B model can test whether domain adaptation of a smaller model provides more value than parameter scaling for this bounded task.

Optional Baseline C: Prompt-only constrained E2B model

Use the same untuned model with the complete structured prompt. This establishes how far prompt engineering alone can go.

Useful ablations

Choose only ablations that support the research questions:

fine-tuning on versus off;
deterministic validator enabled versus raw model output;
compact versus richer runtime context;
thinking mode on versus off, if retained as a formal configuration;
full dynamic NPC context versus reduced context.

Do not include every historical failed model as a final condition. V1 and V2 training failures belong in the development methodology unless they answer a formal research question.
